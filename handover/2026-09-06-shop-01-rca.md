## What the same skill did on rows

The producer read the five files as data, found that the bound state-version profile admits no event family, and declared no Event class: the warehouse row's occurrence, its time with no year or zone, and its untyped item identifiers went to typed gaps rather than to a class the profile could not populate. It declined the supplier-order quantities because the two rows admit three readings and no source states their order; it declined to bucket unknown identifiers under root Entity; it declined to invent a plan grammar string or a valid-time kind. It wrote a row adapter that copies every populated value and carried the source token beside each derivation until the grammar removed it. Every one of the nine rows is populated or gapped. On the axis the document cells measure most, honesty under a rule the source cannot meet, the behaviour is the one run-20 and run-21 showed on prose.

## Root causes, by defect

**A. The skill names no plan grammar for structured sources.** One sentence ("write a source-specific adapter that emits the same neutral population plan") and no grammar string, no root keys, no reference shapes, no valid-time kinds, no byte encoding. Cause: the skill was written from the document path, where the adapter writes the plan and the producer never sees one. Classification: skill gap, Core's.

**B. The staged profile is not its own identity.** `prepare_producer.py` writes the profile as pretty-printed bytes; the compiler identifies the profile by the digest of its canonical bytes. A producer told to cite the profile by the digest of the file it was given cites the wrong thing. The document cells never needed the identity in a producer artifact. Classification: harness staging defect, plus the parent's wrong instruction built on it.

**C. The grammar cannot say "no valid time".** `valid_time` is required with kind INSTANT or ORDER_ONLY, both with a value; a change set whose sources state no domain time has no honest encoding. The producer wrote ORDER_ONLY "0" in all four plans and said so. Classification: grammar expressiveness gap, Core's; it does not bite here because there are no supersessions.

**D. Locators are never resolved.** Core pins source bytes and demands a derivation per field, but `row:N:field` is free text to the compiler. The reviewer of this cell is the first thing that opens the row. Classification: Core gap (Paper-26's finding), the row analogue of the digest nobody recomputed before Core-12.

**E. The review protocol is bound to one surface.** Protocol v2's validator pins the evidence surface to the PDF text layer and the question ids to CQ-01 to CQ-04. A row cell's record cannot be machine-validated. Classification: evaluation-layer gap; the ruling on protocol v3 covers it.

## Why this matters beyond the shop

The paper's claim that an isolated producer can populate under the protocol was demonstrated on one document of prose. This cell shows the protocol's mechanical guarantees transfer to rows (typed refusal, replay, trace, type-only query) and that its instruction layer does not: three of four refusals were the grammar the skill never stated, two of them through the parent. A protocol that only the path already exercised can satisfy is a protocol with an unstated requirement, which is the run-06 lesson again on the other consumer.

## What the review found

Two sessions, 17 rows: 2 SUPPORTED, 5 PARTIAL, 10 UNSUPPORTED; every question PARTIAL. Fifteen rows carry LOCATOR_NOT_RESOLVABLE, two VALUE_MATCHES_ROW. The two sessions saw the same fact and labelled it differently: an unresolvable locator is PARTIAL to the first (the value is in the file, one or two rows earlier) and UNSUPPORTED to the second (a cited row that does not exist supports nothing). That is the grading RCA's threshold problem again, on a mechanical fact rather than a judgement, which makes it easier to close: the label for a locator that does not resolve should be defined, or the case should never reach a reviewer.

**F. The row-numbering convention was never declared.** The producer counts physical lines from 1 with the CSV header as line 1, and said so twice. The review task counts data rows from 0 with the header excluded, because Paper-26 wrote it from the fixture's plans, which do. The skill says nothing; Core treats the locator as free text. My check over the fifteen derivations: under the producer's convention all fifteen resolve and nine values equal the record's; under the task's, two resolve. Classification: protocol defect, the row twin of D. With locator resolution at admission there is one convention, the compiler's, and a plan under another is refused at attempt 4 instead of reviewed at 20:40Z.

**G. The review token asks for equality where the grammar means derivation.** Six derivations equal nothing under either convention: the relations' `relation_type`, a constant the producer pointed at the invoice-identifier field, and the four endpoint identifiers, which the producer minted by prefixing the row's value (`payment:P1` from `P1`). The fixture's own plan derives ORDER_CONTAINS_UNIT from the warehouse row's activity field the same way. A derivation names the field a value came from, not a field that equals it; VALUE_MATCHES_ROW, written for the review by Paper-26 and dispatched by me, would fail the fixture. Classification: review-task defect, the parent's. A DERIVED_FROM_ROW token beside the equality one, or the equality token restricted to properties, is the fix.

Responsiveness, in the sessions' words: CQ-S1 asks which invoices the payment settled and the rows carry a reference relation (a modelling reading the task puts out of scope); CQ-S2's row carries no quantity and the trace no supersession, as the producer declined both; CQ-S3's rows carry no containment relation, the only relation type on the surface being the payment one; CQ-S4's rows do not resolve. Under the producer's convention and a derivation token, the support column would read differently; nothing here re-grades it.

## Fixes, in order of leverage

1. Skill (Core): a structured-source section that states the plan grammar string, the twelve root keys, the closed shapes of adapter, sources, evidence, history_profile, valid_time, derivations, gaps and supersessions, the two valid-time kinds, and the canonical-bytes rule; one worked plan validated by the compiler before the skill ships (the rule in my own CLAUDE.md: every example in a spec is a file run through the validator).
2. Harness: stage the profile as canonical bytes, or carry its identity in the phase-two coordinates as the contract identity is carried.
3. Core: a valid-time kind for "none stated", or `valid_time` optional under a profile whose sources state none.
4. Core: resolve `row:N:field` locators at plan admission against the retained source bytes, typed refusal on a miss; the closure check's precedent, one function in one place.
5. Evaluation: protocol v3 with a declared evidence surface per cell, a declared locator convention, a defined label for a locator that does not resolve, and a derivation token beside the equality token.

## What this does not say

Nothing here measures the shop as a domain: twelve rows, no money, no dates. The cell measures the protocol's second path, and the review's support labels on 17 rows say what the reviewers could resolve under a convention the protocol never declared, and the overseer's check says the nine records are derived from their rows under the producer's; responsiveness on four questions of which one (CQ-S2) cannot be answered by a current-graph query is a caveat stated before the producer ran.
