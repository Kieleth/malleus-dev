## Read-only diagnosis

Two losses must stay separate.

First, retrieval is not invariant to where an allowed value is stored. One
Observation has quantity_kind "quantity of CO2", numeric bounds and a subject
reference to a MeltPhase named "primary melts". The frozen primary-carbon
program requires both lexical groups on the Observation itself. It never
follows the subject while selecting candidates, even though the public graph
read returns that subject. The value exists and is missed. The instrument
count is also stored, on a Campaign with count_scope, but the program requires
a deployment phrase that this row omits. That case additionally lacks the
explicit deployment distinction the original query was designed to preserve.
Neither query was changed after seeing this population.

Second, the population is small and leaves important distinctions outside the
query view. The two Claim records carry disposition, modality, a generic
claim_kind and a subject, but no statement or assertion_locator field. Their
record IDs suggest particular mechanisms; IDs are identifiers, not evidence
that the graph expresses those mechanisms as semantic fields. The history's
public trace still reaches retained assertions. Reading those assertions is a
different evidence view from querying graph fields. It must not silently fill
the answer or become an invented SUPPORTS edge.

The optional fields and existing reads admit this representation. No missing
Core read capability or replay loss was found. Deciding whether the next paper
query may follow subject references is paper work. Requiring source-supported
proposition content, retaining honest gaps and continuing capture are producer
and adopter-policy concerns, not an implicit request for Core to evaluate
answers or infer missing relations.
